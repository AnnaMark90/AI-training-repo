## P1-1. Сводка показывает нули вместо реальных чисел — ✅ ИСПРАВЛЕНО (`2feb9d8`)

**Где:** строки 87–88 на `063c6a5` (сейчас 90–91): `stats.passed`, `stats.failed`.

**Проверка.** Синтетический прогон дал `stats`:

```json
{"startTime":"...","duration":5683.675,"expected":1,"skipped":1,"unexpected":2,"flaky":1}
```

Ключей `passed` и `failed` нет. Сводка из workflow (с возвращённой `p`) вывела:

```
Passed:0 Failed:0 Flaky:1 Skipped:1
```

Реально было 1 passed, **2 failed**, 1 flaky, 1 skipped.

**Последствия.** После исправления P0 шаг станет зелёным и будет писать в Summary `Failed: 0`, даже если тесты упали. Ложная сводка хуже её отсутствия: ей верят.

**Варианты решения:**
1. Минимально: `stats.expected` для Passed, `stats.unexpected` для Failed.
2. Считать по итоговым статусам тестов (`expected`, `unexpected`, `flaky`, `skipped`) обходом `suites`. Тогда числа и список упавших (P1-2) берутся из одного источника.
3. Заменить свой скрипт встроенным репортером `github` (`reporter: process.env.CI ? [['github'], ['html'], ['json', …]] : …`): он сам ставит аннотации на упавшие тесты.

**Статус.** ✅ Применён вариант 1 в `2feb9d8`. Подтверждение в CI до исправления: в запуске 41637887351 сводка показала `Passed: 0` при `7 passed`. После исправления синтетический прогон даёт `1 / 2 / 1 / 1`, а набор из 7 прошедших тестов — `Passed: 7`. Запуск 41641845635 зелёный.

## P1-2. Список упавших тестов неверен — ✅ ИСПРАВЛЕНО (`5107656`)

**Где:** строки 104–105 на `063c6a5` (сейчас функция `collect`, строки 103–112).

```js
const err = (t.results || []).find(res => res.status === "failed");
if (err) out.push(`${spec.file || ""}: ${t.title}`);
```

**Проверка.** Статусы в синтетическом прогоне:

| Тест | `test.status` | статусы попыток |
|---|---|---|
| fail | `unexpected` | `failed`, `failed` |
| timeout | `unexpected` | `timedOut`, `timedOut` |
| flaky | `flaky` | `failed`, `passed` |

Скрипт вывел список `[ 's.spec.mjs: undefined', 's.spec.mjs: undefined' ]`.

**Суть.** Три независимых дефекта:
1. **`t.title` всегда `undefined`.** В JSON-отчёте заголовок хранится у `spec`, а у объекта `test` поля `title` нет. Найдено при проверке, в первом разборе этого пункта не было.
2. **Тесты, упавшие по таймауту, не попадают в список:** их статус `timedOut`, а не `failed`.
3. **Flaky-тест попадает в «Failed tests»,** хотя в итоге прошёл. В CI включён `retries: 1` (`playwright.config.ts:16`), так что это реальная ситуация.

**Последствия.** Даже при правильных числах из P1-1 список упавших бесполезен: вместо имён тестов `undefined`, таймауты пропущены, flaky выдаются за падения.

**Варианты решения:**
1. Брать заголовок из `spec.title` и фильтровать по `t.status === "unexpected"`. Flaky выводить отдельным списком (`t.status === "flaky"`).
2. Перейти на репортер `github` (вариант 3 из P1-1).

**Статус.** ✅ Применён вариант 1 в `5107656`. На синтетическом прогоне в «Failed» попадают `fail` и `timeout`, в «Flaky» — `flaky`, у каждого указаны проект и строка. Запуск 41640708191 зелёный. Упавших тестов в нём не было, поэтому вывод списков в CI ещё не наблюдался.

## P1-3. Трассы с cookie стенда попадают в артефакт публичного репозитория — ⏸ ОТЛОЖЕНО

**Статус.** Отложено по решению от 2026-11-03. Риск остаётся: он сработает при первом упавшем тесте в CI.

**Где:**
- `playwright.config.ts:25` — `trace: 'on-first-retry'`;
- `playwright.config.ts:16` — `retries: 1` в CI;
- строки 68–75 — `upload-artifact` с `playwright-report/`, `retention-days: 30`;
- `gh repo view` — `visibility: PUBLIC`.

**Проверка.** Тест упал на первой попытке, ретрай записал трассу. Трасса оказалась в `report2/data/*.zip` HTML-отчёта. В её файле `trace.network` найден заголовок запроса:

```
"name":"Cookie","value":"_medusa_session=SECRET_COOKIE_VALUE_123"
```

Имя и значение cookie здесь тестовые: их задаёт сервер в синтетическом тесте.

**Суть.** Как только в CI упадёт любой тест, Playwright запишет трассу ретрая с полными заголовками запросов к стенду, включая cookie сессии и админки. HTML-отчёт с трассой загрузится в артефакт. Артефакты публичного репозитория может скачать любой авторизованный пользователь GitHub, и хранятся они 30 дней. В последнем запуске все тесты прошли, поэтому трассы нет: риск ещё не реализовался.

**Последствия.** Утечка активной сессии персонального стенда и учётки админа. Маскирование секретов GitHub работает только для логов, на содержимое артефактов оно не распространяется. `README.md:93` требует приватный репозиторий.

**Варианты решения:**
1. Сделать репозиторий приватным: создать приватную копию и перенести в неё секреты. Это закрывает проблему полностью.
2. Если репозиторий остаётся публичным: `trace: process.env.CI ? 'off' : 'on-first-retry'`, в артефакт загружать только `results.json`, `retention-days: 3`.

## P1-4. Без секретов e2e пропускаются, а запуск зелёный — ⏸ ОТЛОЖЕНО

**Статус.** Отложено по решению от 2026-11-03.

**Где:** строки 50–52 и условия `if` на строках 57, 63, 66, 69, 78.

**Проверка.** Запуск 41612322021 того же коммита `063c6a5`: `Secret SESSION_URL is not set, e2e tests skipped`, джоба `e2e` — **success** за 13 с по UI (16 с по `startedAt`/`completedAt` из API). P0 уже был в коде, но не выполнился.

**Последствия:**
- Зелёный статус не значит, что тесты прошли. Без секретов дефекты в шагах после тестов не видны.
- PR из чужих форков в публичный репозиторий не получают секретов и всегда «зелёные».

**Варианты решения:**
1. При `workflow_dispatch` и для `main` отсутствие `SESSION_URL` должно давать `exit 1`.
2. Отдельная джоба `preflight` с output `has-stand` и `if` на уровне джобы `e2e`. Без стенда джоба получает статус `skipped` (серый), а не `success`. Заодно решает P3-13.
3. Как минимум — запись «e2e skipped» в `$GITHUB_STEP_SUMMARY`.

## P2-5. Шаг сводки влияет на статус джобы; кэш при красной джобе не сохраняется

**Где:** строки 77–78 (нет `continue-on-error`), строки 56–61 (`actions/cache@v4`).

**Проверка.** В упавшем запуске у `Post Cache Playwright browsers` статус `skipped`: `actions/cache` сохраняет кэш только при успешной джобе. После исправления P0 кэш сохранился в 41637887351 и восстанавливался в 41640708191 и 41641845635.

**Последствия.**
- Любая новая ошибка в отчётности (например, битый JSON) снова сделает CI красным при зелёных тестах.
- Кэш не сохраняется в запусках, где упал хоть один тест.

**Варианты решения:**
1. `continue-on-error: true` для `Test summary`.
2. `actions/cache/restore` + `actions/cache/save` с `if: always()`, либо удалить кэш (P3-12).

## P2-6. Скрипт сводки вне lint и typecheck

## P2-7. `concurrency` отменяет ожидающие запуски

**Где:** строки 34–36: `group: e2e-${{ github.repository }}`, `cancel-in-progress: false`.

**Проверка.** По документации GitHub в группе может быть один выполняющийся и один ожидающий запуск. Новый ожидающий отменяет предыдущий ожидающий. В двух проанализированных запусках этого не было: они не пересекались.

**Последствия.** При серии push-ей промежуточные коммиты получают `cancelled` вместо проверки e2e.

**Варианты решения:**
1. Сузить триггеры (P2-8).
2. Workflow-level `concurrency` по `github.ref` с `cancel-in-progress: true`: устаревшие запуски ветки отменяются явно. Job-level группа для стенда остаётся.

## P2-8. Триггер `push` без фильтра, нет `pull_request`

**Где:** строки 2–4.

**Последствия.**

**Варианты решения:**

2. В ветках по push запускать только `quality`.

## P3-15. Smoke-набор выбирается grep по ID

**Где:** `package.json:7`: `--grep "AUTH-01|ADM-01"`.

**Проверка.** `--list` выбирает 4 теста: оба setup, AUTH-01 и ADM-01. Сейчас отбор верный.

**Последствия.** Переименование теста молча исключит его из smoke, а будущий `AUTH-010` попадёт туда случайно.

**Варианты решения.** Тег `{ tag: '@smoke' }` и `--grep @smoke`. Как минимум — регулярка `"(AUTH|ADM)-01:"`.

## P3-16. Права `GITHUB_TOKEN` не заданы явно

**Где:** в workflow нет `permissions:`.

**Проверка.** В логе: `Contents: read`, `Metadata: read`, `Packages: read` — это настройка репозитория по умолчанию.

**Последствия.** Сейчас проблемы нет. Если поменять значение по умолчанию в настройках репозитория, workflow незаметно получит права на запись.

**Варианты решения.** Добавить в workflow `permissions: { contents: read }`.

## Снято после проверки

**`github.event.inputs.run-mode` (строка 67).** Контекст устаревший, но рабочий. При `workflow_dispatch` выражение возвращает выбранный режим. При `push` свойство пустое, и выражение даёт `'test'`, то есть полный прогон, как и задумано. Ошибки нет. Замену на `inputs.run-mode` можно сделать попутно, но проблемой это не является.
